# Отклик — платформа анонимных обращений школьников

Go-бэкенд (REST API на chi + PostgreSQL) для приёма анонимных обращений
школьников, родителей и педагогов к психологам, медиаторам и юристам.

## Требования

- [Docker](https://docs.docker.com/get-docker/) с Docker Compose (входит в
  Docker Desktop для Windows/macOS; в Linux — пакет `docker-compose-plugin`).
- Больше ничего не нужно: Go-зависимости лежат в `vendor/`, образы стянутся
  сами при первом запуске.

## Запуск одной командой (из чистого клона)

```bash
git clone <адрес-репозитория> && cd it-fest-oren
docker compose up --build -d
```

Готово. Поднимаются два контейнера:

| Контейнер | Описание |
|---|---|
| `otklik-db` | PostgreSQL 16 (user `otklik`, пароль `default_password`, БД `otklik`) |
| `otklik-app` | Приложение: **8080** — для заявителей, **8081** — для сотрудников |

При старте автоматически применяются миграции (`internal/db/migrations`)
и создаются seed-данные (категории + демо-пользователи) — только если БД пуста.

### Проверка

```bash
curl http://localhost:8080/api/health
```

Откройте в браузере:

- **http://localhost:8080/** — вкладка «Заявитель»: создание обращения,
  вход по трек-номеру, чат с автообновлением;
- **http://localhost:8081/** — вкладка «Сотрудник»: вход под демо-учёткой.

### Останов и сброс

```bash
docker compose down      # остановить (данные в volume сохранятся)
docker compose down -v   # остановить и удалить все данные (полный сброс)
```

> **Важно:** пароль PostgreSQL считывается только при **первой**
> инициализации volume. Если меняли `POSTGRES_PASSWORD` в
> `docker-compose.yml` — выполните `docker compose down -v` перед новым
> запуском, иначе приложение не сможет подключиться к БД.

## Тестовые учётные записи (создаются при первом старте)

Пароль у всех: `otklik-demo-2026` (меняется через `SEED_DEFAULT_PWD`).
Вход — на вкладке «Сотрудник» (**http://localhost:8081/**).

| Роль | Логин | Пояснение |
|---|---|---|
| **Оператор** | `operator` | очередь новых обращений: назначение эксперта, приоритет, категория, отклонение, завершение, закрытие без ответа (`close-no-response`), возврат на доработку (`return`); аналитика «по себе» |
| **Эксперт (психолог)** | `psychologist1`, `psychologist2` | рабочие обращения: `take → clarify → recommendation → transfer-request → contributors`, чат и внутренние заметки; аналитика «по себе» |
| **Эксперт (юрист)** | `lawyer1` | то же, группа «юрист» |
| **Эксперт (конфликтолог)** | `conflictolog1`* | то же, группа «конфликтолог» |
| **Администратор** | `admin` | админ-панель: аналитика и CSV-выгрузки, пользователи, категории (правила маршрутизации), жалобы; в карточке обращения — смена статуса/приоритета/исполнителя с причиной и записью в журнал; переписка, заметки, текст обращения и закрытие обращений недоступны |

\* `conflictolog1` создаётся только на чистой базе. В базах, засеянных до переименования, конфликтолог остаётся под старым логином `mediator1` — миграция 004 меняет его группу на «конфликтолог».
Пользователя `social1` (социальный педагог) также нужно создать вручную в админ-панели на старой базе — сиды выполняются только на пустой БД.

## Тестовый веб-интерфейс

Встроенный одностраничный UI (без внешних зависимостей, вшит в бинарь
через `go:embed`), доступен и на 8080, и на 8081:

- вкладка **Заявитель** — первый экран «что это за сервис, что происходит
  после отправки, почему это безопасно» с двумя явными точками входа:
  подать обращение и проверить статус по трек-номеру; создание обращения
  (категория или свободный текст; «Не знаю, как это назвать» есть и чекбоксом,
  и пунктом списка категорий), уточняющие вопросы с вариантами ответов,
  вложения (до 5 файлов по 10 МБ, метаданные EXIF/геолокация вырезаются
  на сервере), дописывание обращения после отправки, вход по трек-номеру,
  чат с автообновлением, результат («помогло/не помогло»), оценка, кнопка
  «написать снова» после закрытия; трек-номера сохраняются в localStorage;
  бережный интерфейс: поддерживающие формулировки без давления,
  тон «ты»/«вы» переключается вместе с выбором типа заявителя, подсказки
  формы — в тёплых нейтральных тонах вместо красных;
- вкладка **Сотрудник** — очередь оператора (назначение эксперта, приоритет,
  категория, отклонение, завершение, закрытие без ответа, возврат на
  доработку; обращения с запросом передачи помечены
  бейджем «↔ требуется другой специалист»), рабочий процесс эксперта
  (`take → clarify → recommendation → transfer-request → contributors`),
  чат и заметки с автообновлением (заметки — только специалисту),
  персональная аналитика и CSV-выгрузки, аудит, админ-панель (аналитика,
  выгрузки, пользователи, категории, жалобы, метаданные обращений).

## Модель приватности

Приложение построено вокруг анонимности заявителя и принципа минимальной
необходимости данных для каждой роли:

- **Никакой регистрации.** Заявитель не оставляет имя, e-mail или телефон:
  обращение создаётся анонимно, доступ — только по трек-номеру.
- **Физическое разделение контекстов.** Публичная часть (заявители) и служебная
  часть (сотрудники) слушают на **разных портах** — 8080 и 8081. Маршруты
  сотрудников на публичном порту недоступны в принципе (и наоборот): это
  уменьшает поверхность атаки и упрощает сетевые ограничения (например, служебный
  порт можно закрыть от интернета на файрволе).
- **Секреты хранятся только хешами.** Трек-номера и токены сессий (сотрудников
  и заявителей) лежат в БД как SHA-256 — утечка базы не даёт доступ к
  обращениям. Пароли сотрудников — bcrypt.
- **Проекции по ролям:** заявитель видит минимум (без имён, внутренних заметок
  и аудита), но всегда понимает, на каком этапе обращение: каждому статусу
  сопоставлено понятное объяснение «что происходит дальше», со школьником —
  на «ты», с родителем и педагогом — на «вы»; эксперт — только назначенные
  ему обращения; оператор — рабочие данные очереди; админ — только
  метаданные обращений.
- **Вложения обезличены:** исходные имена файлов отбрасываются (выдаются как
  `attachment.bin`), тип проверяется по фактическому содержимому
  (whitelist MIME), отдача — с `X-Content-Type-Options: nosniff`; лимит —
  5 файлов по 10 МБ.
- **Rate limits:** создание обращений — 5/час с одного IP; попытки входа по
  трек-номеру — 20/час с IP (защита от перебора); логин сотрудников —
  10/минут с IP.
- **Сессии ограничены по времени:** TTL 2 часа (`SESSION_TTL_MIN`).

## Принятые проектные решения

### Трек-номер

Трек-номер — единственный способ доступа заявителя к обращению
(bearer credential: предъявивший верный секрет считается владельцем),
поэтому к нему особые требования:

- Формат `ОТК-X7KD-R9MF-Q3HP`: 12 значащих символов из алфавита без похожих
  символов (`0/1/I/L/O` исключены), генерация криптостойким `crypto/rand`
  — перебор на практике невозможен и дополнительно блокируется rate limit.
- Выдаётся **ровно один раз** при создании обращения и **не восстанавливается**:
  восстановление означало бы возможность идентификации заявителя (хранение
  копии номера у системы). Потерял номер — обращение недоступно, это цена
  анонимности, принято сознательно.
- В БД хранится только SHA-256-хеш нормализованного номера: оператор и БД
  не знают сам номер. Ввод регистронезависим (`ОТК-…` = `otk-…`).

### Уведомления

Отдельная система уведомлений (таблица `staff_notifications`, страницы
оповещений, поллинг ленты) была реализована и **сознательно откачена** как
избыточная для хакатонного объёма. Вместо неё:

- запрос эксперта «требуется другой специалист» виден оператору **бейджем
  «↔ требуется другой специалист»** прямо на карточке обращения в списках
  (очередь и «Все обращения») — без отдельного экрана уведомлений;
- свежесть данных обеспечивается поллингом с интервалом 5 секунд: страница
  заявителя (чат/статус) и открытая карточка сотрудника (чат/заметки/статус)
  обновляются без перезагрузки; фоновое обновление не затирает набираемый
  текст в полях.

Внешние каналы (e-mail/SMS/push) не предусмотрены — заявитель по построению
анонимен и не оставляет контактов.

## Локальный запуск без Docker

Нужны Go 1.24+ и запущенный PostgreSQL. Создайте роль и БД `otklik`, затем:

```bash
export DATABASE_URL="postgres://otklik:default_password@localhost:5432/otklik?sslmode=disable"
go run ./cmd/server
```

(Windows PowerShell: `$env:DATABASE_URL="postgres://otklik:default_password@localhost:5432/otklik?sslmode=disable"`)

## Основные эндпоинты

**Публичные:**
- `GET  /api/health` — живость
- `GET  /api/categories` — активные категории
- `GET  /api/intake-questions` — вопросы анкеты
- `GET  /api/help/crisis` — контакты экстренной помощи
- `POST /api/appeals` — создать обращение → трек-номер (выдаётся один раз!)
- `POST /api/appeals/track` — вход по трек-номеру → сессия заявителя (кука)

**Заявитель** (`/api/appeals/me/...`):
- `GET` — статус, объяснение, описание, рекомендации, чат, история, вложения
- `GET|POST /messages` — чат со специалистом
- `POST /append` — дописать обращение после отправки (не для закрытых)
- `POST /result` — «помогло / не помогло»
- `POST /feedback` — оценка и комментарий
- `POST /complaint` — жалоба на специалиста
- `POST|GET /attachments` — вложения (до 5 файлов по 10 МБ; JPEG/PNG
  перекодируются на сервере — EXIF и геолокация вырезаются)

**Сотрудники** (`POST /api/auth/login` → кука сессии):
- `GET /api/operator/queue` — очередь новых: срочные и просроченные
  первыми; строка содержит `waiting_sec` и `overdue` (ждёт обработки дольше
  SLA — 24 ч, счётчик просроченных выводится в заголовке)
- `GET /api/operator/appeals?status=` — все обращения оператора; фильтр
  `distributed` — контроль распределённых: строка содержит
  `no_reply_sec` (заявитель ждёт ответа специалиста; nil — неотвеченных
  сообщений нет), зависшие дольше SLA поднимаются вверх; текст переписки
  в списке не отдаётся
- `GET /api/expert/appeals?status=&category=&priority=` — «мои обращения» эксперта:
  только назначенные (SQL-фильтрация по участникам), срочные всегда
  сверху и визуально выделены в списке; приоритет эксперт менять не может —
  при несогласии оставляет заметку и запрашивает пересмотр у оператора
  (`transfer-request` с причиной; оператор видит пометку и подсказку)
- `GET /api/admin/appeals|users|categories|complaints` — метаданные для админа
  (в `appeals` — флаги маршрутизации: `no_expert_in_group`,
  `group_overloaded` — подсветка админу обращений без исполнителя по правилу)
- `GET|PUT /api/admin/settings` — рамки маршрутизации: лимит
  активных обращений на специалиста `expert_active_limit` (таблица `settings`,
  миграция 005). Категории и соответствие «категория → группа специалистов»
  админ ведёт в `/api/admin/categories`
- `GET  /api/staff/experts` — специалисты с текущей нагрузкой `active_count/limit`
- `GET /api/operator/queue` — очередь оператора; строки содержат `routing_group`
  и флаги `no_expert_in_group` / `group_overloaded`
- `GET  /api/appeals/{id}` — карточка обращения (эксперт — только свой; админу текст и анкета не отдаются);
  оператору в карточке — `category_suggestion`: подсказка системы по категории
  (keyword-скоринг по тексту и анкете) и `routing` — подсказка
  маршрутизации: группа по правилу, нагрузка каждого специалиста
  группы, рекомендуемый свободный (`free_login`) либо предупреждение
  «все перегружены» (`all_overloaded`, наименьшая загрузка — `least_loaded`);
  назначение по подсказке или вопреки ей — решение всегда за оператором,
  назначение перегруженного требует подтверждения в UI
- `POST /api/appeals/{id}/assign|priority|category` — оператор и админ
- `POST /api/appeals/{id}/reject|complete|close-no-response|return` — оператор
- `POST /api/appeals/{id}/take|clarify|recommendation|transfer-request|contributors` — эксперт (только ответственный)
- `GET|POST /api/appeals/{id}/messages|notes` — чат с заявителем (эксперты-участники)
  и внутренние заметки (видны участникам и оператору — чтение;
  пишут специалисты, заявителю и админу недоступны; визуально отдельный блок)
- `GET|POST /api/appeals/{id}/presence` — «одновременная работа»:
  кто сейчас в карточке и кто печатает ответ (in-memory, TTL 15 с);
  пока другой специалист печатает, поле ввода чата блокируется
- `GET  /api/appeals/{id}/events` — аудит (оператор/админ; история назначений
  и передач)
- `GET  /api/mystats` — персональная аналитика оператора/эксперта («по себе»)
- `GET  /api/export/appeals` — CSV-выгрузка: оператор/админ — все, эксперт — свои

## Архитектура

```
cmd/server        точка входа
internal/config   конфигурация из окружения
internal/db       подключение, миграции (go:embed), seed
internal/domain   домен: статусы, трек-номера, кризис-эвристика
internal/store    все SQL-запросы
internal/httpapi  REST API: маршруты, аутентификация, проекции
```

Безопасность: трек-номера и сессионные токены хранятся только в виде
SHA-256 хешей; заявитель видит минимум (без имён, заметок и аудита);
админ — только метаданные; вложения очищаются от исходных имён файлов.

## Нереализованное (осознанные ограничения)

- **Внешние уведомления** (e-mail, SMS, push) — не заявителю (анонимность),
  не сотрудникам (выбран бейдж в списках, см. выше).
- **TLS/HTTPS** сервер не терминирует сам: для продакшена нужен reverse proxy
  (nginx/Caddy) перед портами; флаг `COOKIE_SECURE=1` уже поддерживается.
- **Rate limiter в памяти** — однопроцессный: счётчики сбрасываются при
  рестарте и не шарятся между инстансами.
- **Смена/сброс пароля сотрудника через API** не реализована (пароль задаётся
  при создании пользователя админом; смена — пересозданием записи).
- **Пагинация списков** обращений/чатов отсутствует — отдаются целиком
  (для демо-объёмов достаточно).
- **Политика хранения данных**: автоудаление/архивация обращений по сроку
  и «право на забвение» не реализованы.
- **Антивирусная проверка вложений** — только whitelist MIME-типов по
  содержимому, внешних сканеров нет.
- **Фоновые задачи** (SLA-напоминания, эскалация просроченных обращений) —
  нет планировщика.
- **Локализация** — только русский язык.
- **Тесты** — только юнит-тесты (`internal/domain`, `internal/httpapi`);
  интеграционных и e2e-тестов нет.

```bash
go build ./...   # сборка

```

Вложения хранятся в volume `appdata`, БД — в volume `pgdata`.
