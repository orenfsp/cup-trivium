# Отклик (cup-trivium)

Анонимная платформа приёма обращений: заявитель создаёт обращение без регистрации и общается со специалистом по трек-номеру, сотрудники (оператор, эксперты, админ) работают через служебный порт.

## Требования

Нужен только Docker с Docker Compose (в Docker Desktop для Windows/macOS он уже есть, на Linux поставьте пакет `docker-compose-plugin`). Больше ничего — Go-зависимости лежат в `vendor/`, нужные образы скачаются сами при первом запуске.

## Запуск

```bash
git clone <адрес-репозитория> && cd cup-trivium
docker compose up --build -d
```

Поднимаются два контейнера:

- `otklik-db` — PostgreSQL 16 (user `otklik`, пароль `default_password`, база `otklik`)
- `otklik-app` — само приложение, порт 8080 для заявителей, 8081 для сотрудников

При старте автоматически накатываются миграции (лежат в `internal/db/migrations`) и создаются seed-данные — категории и демо-пользователи. Только если база пуста.

Проверить, что всё живо:

```bash
curl http://localhost:8080/api/health
```

Дальше открываем в браузере:
- http://localhost:8080/ — вкладка «Заявитель» (создание обращения, вход по трек-номеру, чат с автообновлением)
- http://localhost:8081/ — вкладка «Сотрудник» (вход под демо-учёткой)

Остановить или снести всё:

```bash
docker compose down      # остановить, данные в volume останутся
docker compose down -v   # остановить и удалить все данные (полный сброс)
```

Важно про пароль PostgreSQL: он читается только при первом создании volume. Если поменяли `POSTGRES_PASSWORD` в `docker-compose.yml`, сначала сделайте `docker compose down -v`, иначе приложение не подключится к базе.

## Тестовые учётные записи

Создаются при первом старте. Пароль у всех одинаковый: `otklik-demo-2026` (можно поменять через переменную `SEED_DEFAULT_PWD`). Вход — на вкладке «Сотрудник», http://localhost:8081/.

- `operator` — оператор, очередь новых обращений: назначение эксперта, приоритет, категория, отклонение, завершение
- `psychologist1`, `psychologist2` — эксперты-психологи, рабочие обращения: take → clarify → recommendation → transfer-request → close-no-response, чат, заметки
- `lawyer1` — то же самое, но юрист
- `mediator1` — то же самое, но медиатор
- `admin` — администратор: пользователи, категории, жалобы, метаданные обращений

## Тестовый веб-интерфейс

Внутри есть одностраничный UI без внешних зависимостей (вшит в бинарь через `go:embed`), он доступен и на 8080, и на 8081.

Вкладка «Заявитель»: создание обращения (категория или свободный текст, ответы на анкету), вход по трек-номеру, чат с автообновлением, результат «помогло/не помогло», оценка, жалоба. Трек-номера сохраняются в localStorage.

Вкладка «Сотрудник»: очередь оператора (назначение эксперта, приоритет, категория, отклонение, завершение; обращения с запросом передачи помечены бейджем «↔ требуется другой специалист»), рабочий процесс эксперта (take → clarify → recommendation → transfer-request → close-no-response), чат и заметки с автообновлением, аудит, админ-панель (пользователи, категории, жалобы, метаданные обращений).

## Приватность

Всё приложение построено вокруг анонимности заявителя и принципа «каждая роль видит минимум необходимого»:

- Никакой регистрации. Заявитель не оставляет имя, e-mail или телефон — обращение создаётся анонимно, доступ только по трек-номеру.
- Публичная часть (заявители) и служебная (сотрудники) слушают на разных портах — 8080 и 8081. Маршруты сотрудников на публичном порту недоступны в принципе, и наоборот. Это уменьшает поверхность атаки и позволяет, например, просто закрыть служебный порт на файрволе.
- Секреты хранятся только хешами: трек-номера и токены сессий (и сотрудников, и заявителей) лежат в базе как SHA-256, так что утечка базы не даёт доступ к обращениям. Пароли сотрудников — bcrypt.
- Проекции по ролям: заявитель видит минимум (без имён, внутренних заметок и аудита), эксперт — только назначенные ему обращения, оператор — рабочие данные очереди, админ — только метаданные обращений.
- Вложения обезличены: исходные имена файлов отбрасываются (наружу выдаются как `attachment.bin`), тип проверяется по фактическому содержимому через whitelist MIME, отдача с `X-Content-Type-Options: nosniff`. Лимит — 5 файлов по 10 МБ.
- Rate limits: создание обращений — 5 в час с одного IP, попытки входа по трек-номеру — 20 в час с IP (защита от перебора), логин сотрудников — 10 в минуту с IP.
- Сессии живут 2 часа (`SESSION_TTL_MIN`).

## Принятые проектные решения

### Трек-номер

Трек-номер — единственный способ доступа заявителя к обращению (bearer credential: кто предъявил верный секрет, тот и владелец), поэтому к нему особые требования:

- Формат `ОТК-X7KD-R9MF-Q3HP`: 12 значащих символов из алфавита без похожих символов (0, 1, I, L, O исключены), генерация через криптостойкий `crypto/rand`. Перебор на практике невозможен и вдобавок блокируется rate limit'ом.
- Номер выдаётся ровно один раз при создании обращения и не восстанавливается. Восстановление означало бы, что система хранит копию номера и может идентифицировать заявителя. Потерял номер — обращение недоступно; это цена анонимности, решили так сознательно.
- В базе лежит только SHA-256-хеш нормализованного номера, то есть оператор и сама БД не знают номер целиком. Ввод регистронезависимый: `ОТК-…` = `otk-…`.

## Основные эндпоинты

Публичные:

- `GET  /api/health` — проверить, что работает
- `GET  /api/categories` — активные категории
- `GET  /api/intake-questions` — вопросы анкеты
- `GET  /api/help/crisis` — контакты экстренной помощи
- `POST /api/appeals` — создать обращение, в ответ придёт трек-номер (выдаётся один раз!)
- `POST /api/appeals/track` — вход по трек-номеру, ставится сессионная кука заявителя

Заявитель (`/api/appeals/me/...`):

- `GET` — статус, объяснение, рекомендации, чат, история, вложения
- `GET|POST /messages` — чат со специалистом
- `POST /result` — «помогло / не помогло»
- `POST /feedback` — оценка и комментарий
- `POST /complaint` — жалоба на специалиста
- `POST|GET /attachments` — вложения (до 5 файлов по 10 МБ)

Сотрудники (сначала `POST /api/auth/login`, получите куку сессии):

- `GET /api/operator/queue` — очередь оператора
- `GET /api/operator/appeals?status=` — все обращения оператора
- `GET /api/expert/appeals?status=&category=&priority=` — список эксперта
- `GET /api/admin/appeals|users|categories|complaints` — метаданные для админа
- `GET  /api/appeals/{id}` — карточка обращения (эксперт — только свой)
- `POST /api/appeals/{id}/assign|reject|complete|priority|category` — оператор
- `POST /api/appeals/{id}/take|clarify|recommendation|transfer-request|close-no-response|contributors` — эксперт
- `GET|POST /api/appeals/{id}/messages|notes` — чат и внутренние заметки
- `GET  /api/appeals/{id}/events` — аудит (оператор/админ)

## Архитектура

```
cmd/server        точка входа
internal/config   конфигурация из окружения
internal/db       подключение, миграции (go:embed), seed
internal/domain   домен: статусы, трек-номера, кризис-эвристика
internal/store    все SQL-запросы
internal/httpapi  REST API: маршруты, аутентификация, проекции
```

По безопасности: трек-номера и сессионные токены хранятся только в виде SHA-256-хешей.
